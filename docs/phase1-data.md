# Phase 1 data foundation

## Discovery and compatibility

The server is strict TypeScript/Express, Prisma 7 with the pg adapter, and
PostgreSQL in the backend-only `vendora` schema. Prisma deploy tracks migrations.
`User.id` is UUID (`server/prisma/schema.prisma`); registration in
`server/src/services/auth.service.ts` creates a business and an owner membership.
Existing users and businesses are not altered. The requested business `user_id`
is represented by `business_memberships.userId`, and `name`/`created_at` by
existing `businessName`/`createdAt`. A second ownership mechanism would conflict
with existing registration and multi-user shops.

## Design (M2)

All new IDs are UUIDs, generated by Prisma (raw SQL callers supply IDs).
All six tables have required, indexed `business_id` referencing the existing
business with DELETE RESTRICT. Business deletion requires explicit ledger cleanup.
New timestamps use timestamptz(3); reporting boundaries use Africa/Lagos.

| Table | Columns beyond id/business_id | Constraints and indexes |
| --- | --- | --- |
| products | name text, unit_price bigint, cost_price bigint nullable, stock_qty int default 0, low_stock_at int default 5, created_at | Nonnegative prices/stock/threshold; unique (business_id,id); GIN name trigram |
| customers | name text, phone text nullable, created_at | Unique (business_id,id); GIN name trigram |
| sales | customer_id UUID nullable, total bigint, amount_paid bigint default 0, created_at | Nonnegative total; 0 <= paid <= total; unique (business_id,id); (business_id,created_at) |
| sale_items | sale_id UUID, product_id UUID, quantity int, unit_price bigint | Positive quantity; nonnegative price; sale_id index; composite same-business sale/product FKs |
| payments | sale_id UUID, amount bigint, created_at | Positive amount; sale_id index; composite same-business sale FK |
| expenses | description text, amount bigint, category text nullable, created_at | Positive amount; (business_id,created_at) |

Names/descriptions are nonblank. All unmarked fields are NOT NULL. Customer
and product deletion is restricted when referenced, preserving history. Sale
deletion cascades to its items and repayments. Optional customer means walk-in;
named customer references are restricted. Composite FKs prevent tenant mixing
even when a caller supplies valid UUIDs belonging to another business.

Every monetary column is a PostgreSQL BIGINT with a database comment stating
integer kobo; Prisma exposes bigint, so serialize explicitly at future API edges.
Debt is always `total - amount_paid`; no debt table exists. `amount_paid` includes
checkout tender plus later payments. Phase 2 must insert a repayment and increment
amount_paid atomically under a sale row lock; payment rows represent repayments
only, not initial tender. No accounting triggers or APIs are introduced here.

Trigram GIN indexes support indexed substring matching (`ILIKE '%indomi%'`) and
similarity matching. `pg_trgm` is installed in public; an existing installation
must also be in public. Down removes only Phase 1 tables, retaining this shared
extension. Trigram indexes are also declared in Prisma. Custom CHECK constraints
and column comments are owned by the SQL migration; review future generated
Prisma migrations for their preservation.

## Run

From `server`, `npm run phase1:check` creates its own disposable local PostgreSQL
cluster, applies existing auth migrations, deploys Phase 1 twice, rolls it down,
redeploys, seeds twice, and runs reports plus constraint/tenant tests. It never
connects to the configured application database. Temporary cluster files are
retained in the OS temp directory for diagnosis; the server is stopped on
completion. The PostgreSQL 18 test cluster uses synchronous I/O and asynchronous
`pg_ctl stop` on Windows to avoid orphan workers and blocked output pipes during
the dependency's default forced shutdown.
Graceful shutdown allows up to 120 seconds for the local disk checkpoint;
the previous 20-second limit was insufficient on this machine. The final full
Phase 1 run completed with exit code 0, including graceful shutdown.
Use `npm run phase1:check -- --auth` to also run the unchanged auth integration
suite on a separate UTF-8 database in that cluster. Redis integration remains
skipped unless TEST_REDIS_URL is configured. Captured results are in
`docs/phase1-verification.txt`. The standalone auth test's default embedded
database failed once with an uninformative schema-engine error; the same suite
passed using the explicit UTF-8 test database. That initial failure's cause
is unconfirmed; no auth files were changed to bypass it.

For an operator-provided local/demo database (database name must end `_demo` or
`_test`), configure `DIRECT_URL` via the existing `.env` mechanism and run:

```sh
npm run db:deploy
npm run generate
npm run phase1:seed
npm run phase1:verify
npm run phase1:constraints
```

Seed/verification refuse NODE_ENV=production and remote hosts. Seed uses a reserved
fixed UUID namespace, disabled demo user with an invalid password hash, synthetic
phone, exact identity checks and a transaction/advisory lock. It refuses collisions
or unexpected memberships and only deletes ledger rows for its own marked shop;
it never deletes users or businesses. No real phone or login credentials are used.

To undo Phase 1 only, using the same migration credential:

```sh
npm run phase1:down
```

This intentionally deletes the six new tables and their data, never auth tables.
The down script atomically removes only the Phase 1 Prisma migration record so
`npm run db:deploy` can reapply it. It refuses if later migrations are present.
Reapply `prisma/runtime-grants.sql` after deployment for the runtime role.

Reports are parameterized with the demo business UUID. Today is the current
Lagos calendar day; last seven days includes today and six previous days; this
week begins Monday in Lagos. Values printed are integer kobo, never naira floats.
